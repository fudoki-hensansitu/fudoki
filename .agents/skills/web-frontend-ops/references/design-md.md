# DESIGN.md に何を書くか

repo root の `DESIGN.md` は hallmark（anti-AI-slop design skill）が管理する、画面のデザイン規範の正本。audit で指摘を受けて直すとき、次の2つを混ぜやすい。

- **仕様レベルの事実を書かない。** 「団体は62件」「収録していない団体も空のページを持つ」のような、増減する仕様の状態は書かない。書いた瞬間から、ページや団体が増えるたびにこの文書だけが古くなる。`README.md` からも同種の記述を消した経緯があり、同じ失敗を `DESIGN.md` で繰り返さないこと。
  - Why: `DESIGN.md` の役目は「どの画面にどの規範が効くか」というデザイン言語の正本であって、プロダクトの現在状態のスナップショットではない。
  - How to apply: 書いてよいのは色・タイポグラフィ・レイアウト・コンポーネントの規範と、その規範がどの画面種別（例: 報告 / 読み物）に効くかの線引きだけ。「何がいくつあるか」は書かない。
- **作業中の手戻り・試行錯誤の経緯を `⚠️` として残さない。** 「一度 X をやったが Y だったので Z に直した」という自分の作業ログは、プロジェクトの学びではなく単なる経緯であり、書くと後から読む人が「今も有効な制約」と「もう関係ない昔話」を区別できなくなる。
  - Why: `DESIGN.md` 内の既存の `⚠️` 注記（例: 警告に色を与えない・判断の有無を色で言わない）は、いずれも「今も守るべき制約とその理由」であって、いつ気づいたかの時系列ログではない。同じ形式に見えても中身が違う。
  - How to apply: `⚠️` を書く前に「これは今も有効な制約か、それとも単に自分が今回の作業で一度間違えて直しただけか」を自問する。後者なら書かない（必要なら git 履歴で追える）。
