# PR の CI 待ちを数分にする

担当者: wwwyo / Claude
更新日: `2026-11-15`
状態: Draft

## Summary

PR の check が待たせる理由は3つある。全件 build になる PR が重いこと、他の PR の merge で check をやり直すこと、CI の土台（Actions のキャッシュ）が脆いこと。本書は3つをこう直す。

- **土台**: main の store が、build の入力（取り込みの表）を1つにまとめた束を R2 に置く。PR の check と同期はそれを1回読む。キャッシュが消えても、R2 を表の数だけ読みに行かない
- **やり直し**: 受領書を R2 へ移す（[受領書の設計](../ingestion-receipts/dd.md) の段階2・3）。merge の順で記録が古くならず、R2 にまだ無い表を読んで 404 になることもなくなる
- **重さ**: 全件 build の時間を #731 の後で測り直す。10分を超えるときだけ、変えたモデルとその下流だけを build する仕組み（dbt の `state:modified+` と `--defer`）を足す

## Background

2026-11-15（UTC の 0 時から 16 時）に回った run を数えた。

| workflow | 成功 | 失敗 | 取り消し |
|---|---|---|---|
| ingestion-store-check（PR） | 31 | 17 | 10 |
| sync-d1（main） | 7 | 6 | 24 |

成功した PR の check にかかった時間は次のとおり。

- 自治体単位（取り込みの PR）: 1〜6分
- 全件（cofog_rules.csv・dbt のモデル・columns.json の PR）: 24〜25分

失敗の内訳は3つに分かれる。

1. **merge 順のすれ違い**: 変換器の PR（#725）が、check の済んだ取り込み PR（#713）より先に main に入った。#713 の記録が古くなり、main の store が止まった。R2 に表が無いので、他の取り込み PR の check も 404 で落ちた。#736 で記録し直すまで続いた
2. **キャッシュの消失**: 14:40 に Actions の `pipeline-cache`（約3GB）が消えた。repo の上限（10GB）で追い出されたとみている。全件 build が約3,000個の表を `cf r2 objects get` で1個ずつ取りに行き、Cloudflare REST API の上限（アカウント全体で5分に1,200リクエスト）に当たって 429 で落ちた。落ちた回は取れた分だけを保存するので、キャッシュはなかなか戻らなかった。#745 で、429 のときは待って取り直すようにした
3. **全件 build の重さ**: 全件の check は1本25分かかる。そのうち dbt の `main.project` が20分前後を占めていた。#731 で直したが、直した後の時間はまだ測っていない

## Goals / Non-Goals

- 取り込みの PR の check は、今と同じ数分に保つ
- 全件の PR の check を10分以内にする
- 他の PR が merge されても、check の済んだ PR をやり直さなくてよい
- Actions のキャッシュが消えても、check と同期が落ちない。キャッシュが無い回の遅れは数分にとどめる
- 本番に出る数字の検査（保存前の関門と dbt の検査）は弱めない
- D1 への同期の方式（写しとの差分）は変えない
- 出典・OCR 結果の保存と、変換し直しの方式は変えない

## Design

### 1. build の入力を R2 の1つの束にする

main の `ingestion:store` は、受領書の一覧を書いたあとに、一覧にあるすべての表の Parquet を1つの束（`tar` を zstd で圧縮）にまとめ、R2 の `fiscal/ingestion/bundle.tar.zst` に置く。束には、受領書の一覧の sha256 を書いた目印のファイルを入れる。束を作り直すのは、受領書の一覧が変わった回だけにする。

`prepare.py --remote` は、表を R2 から1個ずつ取る前に束を1回読む。束から出した Parquet は、受領書の sha256 とバイト数を確かめてから手元のキャッシュに置く。束に無い表と sha が合わない表だけを、今までどおり1個ずつ取る。

- 大きさ: 2026-11-15 の受領書の一覧（1,583表）が指す Parquet は、合計で約88MB だった。束は `cf` の REST の上限（1オブジェクト300MB）に収まる
- 事業評価の入力（`ingestion/project` の `load(remote=True)` が読むもの）も同じ束に入れるかは、大きさを測って決める
- Actions の `pipeline-cache` は、出典・OCR 結果・事業の PDF を読んだ結果のためだけに残す。これらを使うのは変えた管理 JSON の変換し直しだけで、読むファイルの数は少ない

**カウンターファクト**:
- *R2 の S3 互換 API で読む*: 1,200リクエストの上限は無くなる。ただし約3,000回の往復は残り、R2 の Access Key を GitHub secret に置く手間も要る。束なら新しい secret は要らない。束が300MB を超えたら S3 の multipart に切り替える
- *Actions のキャッシュを追い出されにくくする*: 上限の10GB は repo 全体で分け合っている。PR の branch ごとの generic-observation も増えるので、守り切れない
- *束をやめて warehouse（DuckDB）ごと置く*: 3の `--defer` に使えて便利だが、大きさが300MB を超える見込みで、S3 API が要る。3が要るとわかってから検討する

### 2. merge の順で check をやり直さない

[受領書の設計](../ingestion-receipts/dd.md) の段階2・3で解ける。

- 段階2で、build は R2 の受領書の一覧から表を選ぶ。受領書が無い管理 JSON（merge されたが、まだ保存されていない）は、前の受領書のまま build するか、build から外して報告する。404 では落ちない
- 段階3で、管理 JSON から表の記録を消す。check の後に変換器が main に入っても、記録が古くなることがない。main の store は今のコードで変換し、関門を通ったものを置く

本書で新しく決めることは無い。段階2・3を、1の束より先に進める。

### 3. 全件の check を軽くする（測ってから決める）

#731 の後に全件 build が何分かかるかを、sync-d1 と全件の PR の check のログで測る。

- 10分以内なら、今の全件 build のままにする。全自治体を通す検査がいちばん確かで、仕組みも増えない
- 10分を超えるなら、PR の check を `dbt build --select state:modified+ --defer --state <main の manifest>` に替える。変えたモデルとその下流だけを build し、変えていない上流は main の結果を読む。main の同期は今のまま全件を build し、その `manifest.json` と warehouse を R2 に置いて、比べる相手にする

`--defer` が読む main の warehouse は300MB を超える見込みなので、置くには S3 API が要る。3に進むときに、1の束と合わせて切り替える。

### 進める順

1. 全件 build の時間を測る（今日の sync-d1 と全件の PR の check。追加の作業は無い）
2. 受領書の段階2・3（合意済み）
3. build の入力の束（1）
4. 1の結果が10分を超えていたら、3の `state:modified+`

## Risks

- **束と受領書のずれ**: 束を作る前に store が落ちると、束は古いままになる。読む側は表ごとに受領書の sha を確かめ、合わない表は1個ずつ取る。古い束でも間違った表は build に入らない
- **束の作り直しの重さ**: 受領書の一覧が変わるたびに、約88MB を組み直して置く。main の store job で数十秒の見込みだが、最初の実装で測る
- **全件の check を `state:modified+` に替えた場合**: 下流に無い自治体の不整合は、PR では見えなくなる。merge 後の全件 build で見つかったら、その PR を直す。同期は止めない（受領書の設計の、管理 JSON ごとの失敗の切り離しと同じ扱い）
