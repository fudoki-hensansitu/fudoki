# 事業名で事業の評価を引く — 設計

担当者: wwwyo / Claude / Codex
更新日: `2026-10-14`
状態: In Review — 試行完了。現在の方法での拡大は見送り、推奨設定とプロンプト案を記録

## Summary

事業名から自治体の評価資料の頁を引くため、Cloudflare AI SearchでPDFの全文検索と意味の近さによる検索を併用する（hybrid）。通常は最大5 chunkを返し、正式名称を優先して検索する。候補の取得と引用の正しさを分けて確かめる。

最大10件・271問の試行では頁・引用の取り違えが拡大の閾値を超えた。以下の推奨は次の検証の開始条件であり、最適な設定・プロンプトを選定した結果ではない。観測と合否は [試行記録](trial.md) に残す。

## Goals / Non-Goals

- Goal: 団体・評価対象年度・事業を識別して評価資料の頁を引き、目標・実績・評価・課題・方向性を原典と対応づける。
- Non-Goal: この試行だけで公開・ほかの資料への拡大を決めること。評価資料の金額を財政データの答えに使うこと。

## Background

要件は [PRD](prd.md)。原典の選定、検索の登録、検索・回答の条件をここで決める。現在ある検索インスタンスは文字の読めるPDF用の1つだけで、OCR用を分けるのは今後の設計である。検索は管理されたAI Searchに任せる。Worker bindingで呼べるほか、REST APIやCLIでも呼べるため、自前Workerの実行は必須ではない（[公式API](https://developers.cloudflare.com/ai-search/api/search/workers-binding/)）。今回の検証は`cf` CLIから呼び出した。

## Design

### 原典の選定

事業の評価の資料は、団体ごとの選定ファイル（`pipeline/source_selection/<団体>.json`）に、金額の原典とは別の配列 `evaluation_selections` として持つ。型は `schema.ts` の `evaluationSelectionSchema`。

```jsonc
"evaluation_selections": [{
  "target": { "jurisdiction": "131172", "fiscal_year": 2025, "document_kind": "settlement" },
  "candidates": [{ "id": "representative", "title": "...", "landing_url": "...", "inspected_at": "...",
    "files": [{ "download_url": "...", "sha256": "...", "format": "pdf", "pdf_type": "text", "pages": null }] }],
  "selected_candidate_id": "representative",
  "archive": null,
  "reason": "..."
}]
```

- **target は評価する実績の決算を指す。** 令和7年度の実績を令和8年度に評価した資料なら、target は令和7年度の決算になる。同じファイルの `selections` に同じ target が無ければ止める。評価の年度が決算とずれることを防ぐ。
- **ファイルは会計・お金の向きを持たない。** 評価の資料は会計ごとに分かれていないので、頁範囲（`pages`、null は全頁）だけを持つ。選定済みのファイルには sha256 が必須。
- **`selections` に混ぜない。** `document_kind` は金額の資料区分の語彙で、API の enum もここから取る（[ADR 0022](../../adr/0022-serve-marts-via-worker-d1-rest-and-mcp.md)）。取り込みと dbt は `selections` だけを読むので、別の配列なら金額の処理は変わらない。
- **ファイルは分けない。** 選定の調査は団体の公式の頁を団体単位で見て進める。別のファイルにすると、団体の記録が2か所に分かれる。
- **資料の名前でなく中身で選ぶ。** 主要施策の成果説明書の中身は団体ごとに違い、目黒区の「主要な施策の成果等報告書」は款・項・目ごとの金額の表と不用額の理由だけで、評価の記述が無い。目標と実績、評価の区分、課題、今後の方向のどれかが書かれた資料を選ぶ。
- **保存は公開・拡大の前に行う。** 第1段は URL と sha256 の固定までで、`archive` は null だけを受ける。AI Search の built-in storage にも PDF が残るが、インスタンスを消すと一緒に消え、作り直しにも原典が要るので、原典の保管場所にしない。第1段で自治体の URL から消えた資料は、sha256 で同じものを探すか選び直す。選び直した資料では、それまでの測定を検証し直せない。保存するときの R2 の key は `fiscal/source-selection/<団体>/<年度>/settlement-evaluation[-<n>].pdf` とし、決算書の key（`.../settlement[-<n>].pdf`）と分けて `archive.ts` の連番の検査とぶつけない。保存を入れるときに `archive` の型と `archive.ts` を広げる。

#### 試行の2団体（2026-10-13 選定）

| 団体 | 資料 | 形 | 読み方 |
|---|---|---|---|
| 中野区（131148） | 令和7年度主要施策の成果 本冊63頁・別冊75頁 | 別冊は施策ごとの評価シート（成果指標の目標と実績・良かった点と要因・今後の戦略、主な事業ごとの実績・効果と次年度の方向性（継続・拡充・縮小・廃止）） | text |
| 北区（131172） | 令和8年度北区事務事業評価（評価対象は令和7年度）108頁 | 1事業1頁（目的・予算額と決算額・アウトプットとアウトカムの計画と実績・事業の状況と課題・進捗度 S〜E・評価区分） | text |

中野区は施策の単位で、目との対応が多対多になる。北区は事業の単位で、1頁が1事業になる。決算の marts は両団体とも令和7年度がある。府中市（令和7年度実績、364事務事業、1事業1シート、A〜D の区分）は、2団体で測った後に広げる候補とする。

ほかの団体の公表状況（2026-10-13 調査）: 令和7年度実績の評価が出ているのは中央区・中野区・杉並区・北区・立川市・府中市・小金井市・東大和市（13事業）・八王子市（Power BI）。多くの団体は令和6年度実績の評価までで止まっている。

### 検索の基盤と登録の形

Cloudflare AI Search を使う。原典の PDF をそのまま built-in storage に入れ、区切りと文字の抜き出しは AI Search に任せる。自前で md に起こさない。

- **PDF はそのまま入れる。** AI Search は PDF を Markdown に変え、頁の境目に頁の見出し（OCR なしは `### Page N`、OCR ありは `<!-- page N -->`）を入れて区切る。chunk は大きさで区切られるので、2頁が一つの chunk に混ざることがあるが、受け手の AI が頁の見出しで読み分ける。
- **大きい PDF だけ頁の範囲で分ける。** OCR なしで受けるのは 4MiB まで（新宿区 37MB、小金井市 30MB、中野区の別冊 6.9MB は超える）。分けたファイルには、元の物理頁の開始をメタデータに持たせ、chunk の頁の見出しに足して原典の頁に戻す。
- **custom metadata**（1インスタンス5項目まで、文字列で絞れるのは先頭64バイトまで）: `jurisdiction`（text）・`fiscal_year`（現索引はnumber）・`origin_sha256`（text）・`page_offset`（number。分けたファイルの開始頁−1、分けなければ0）・`document`（text。資料の種類）。例えば分割PDFの7頁に`page_offset: 38`を足すと原典の物理45頁となる。年度filterの型と挙動は後述の推奨設定で扱う。
- **tokenizer は `trigram`。** 3文字ずつの断片で照合する方式で、今回の日本語資料では文中の部分一致に使う。全文検索で2文字以下の語だけに頼らず、3文字以上の特徴的な語を使う。`keyword_match_mode: or` は検索語のいずれかの一致を許し、`and` はすべての一致を要求する。`or`で候補を広く取り、受け手が事業の一致を確かめる（[公式仕様](https://developers.cloudflare.com/ai-search/configuration/indexing/keyword-search/)）。
- **埋め込みは `@cf/qwen/qwen3-embedding-0.6b`**（8,192 tokenまで）。`@cf/baai/bge-m3`は512 tokenまでなので、評価シート1頁（約3,000 token）を扱う今回の条件ではQwenを選んだ。埋め込みモデルはインスタンス作成時の`embedding_model`で指定でき、作成後は変更できない。検索ごとに切り替えるものではなく、比較するには別インスタンスを作る。モデル間の精度比較は未実施である（[モデル設定](https://developers.cloudflare.com/ai-search/configuration/models/)、[対応モデル](https://developers.cloudflare.com/ai-search/configuration/models/supported-models/)）。
- **OCR はインスタンスを分ける。** OCR を有効にすると文字の層がある頁にも OCR がかかり、表の構造は良くなるが、文字を誤る（「令和」が「合和」、「実績」が「实績」、「決算額」が「决算额」など簡体字に寄る）。文字の読める資料は OCR なしのインスタンスに入れる。
- **文字の層が壊れた PDF は OCR で直らない。** 目黒区の分冊（50頁）を OCR ありで入れると、34頁は化けた文字の層がそのまま使われ、OCR がかかったのは8頁だけだった（8頁は空）。選定で `pdf_type: scan` にした資料は、頁を画像にした PDF に変えてから OCR ありのインスタンスに入れるか、既存の OCR（`ingestion/lib/scan_ocr.py`）で読む。試行の2団体はどちらも text なので、第1段では扱わない。
- **作り直せること**: 抜き出しと区切りは AI Search が行うので、同じ原典から同じ索引ができるとは限らない。要件は「固定した原典から作り直せる」ことで、検索の候補は数字の答えに使わないので、これで足りる。

#### 結果に返るもの（2026-10-13 に確かめた）

- chunk ごとに `item.key`・`item.metadata`（登録した custom metadata）・`text`・`score`。hybrid では `scoring_details` に `vector_score`（0〜1）と `keyword_score`（BM25）が分かれて返る。
- 旧リクエストで`score_threshold: 0`を送っても、意味の近さが0.40未満の候補は返らなかった。2026-10-14の追加検証で、リクエストの正しい指定名`match_threshold: 0`なら0.4未満も返ることを確認した。インスタンス設定の`score_threshold`と検索リクエストの指定名を混同しない。
- 意味の近さのスコアは 0.40〜0.67 に固まり、正解と不正解の差が小さい。

### 推奨する検索設定

対象は今回の2団体・2025年度・文字の読めるPDF。通常の最大件数は利用者の指定で5件とする。**測定後に変更した現行設定は最大5件であり、下表全体を明示して適用した回答精度の検証は未実施である。**

| 設定 | 推奨する開始値 | 判断理由 |
| --- | --- | --- |
| `retrieval_type` | `hybrid` | 正式名称の一致と、言い換えの意味の近さを併用 |
| `fusion_method` | `rrf` | 測定した方式を維持。ほかの融合方式との比較は未実施 |
| `keyword_tokenizer`（索引） | `trigram` | 日本語の文中の部分一致を使う |
| `keyword_match_mode` | `or` | 候補を取りこぼしにくい側から始める |
| `max_num_results` | `5` | 本文量を抑える利用上の選択。精度の最適値とは未確認 |
| `match_threshold`（検索リクエスト） | `0.4` | 追加検証の基準値を明示し、条件を固定する |
| `context_expansion` | `0` | まず返されたchunkを全件読む。隣接chunk追加の効果は未測定 |
| query rewriting・reranking・cache | 検証中は無効 | 自動変更やキャッシュの影響を分けて比較する |

`max_num_results`は返すchunk数の上限であり、5件が必ず返るわけではない。1 chunkには複数の頁・事業が含まれ得る。`match_threshold`はhybridの融合後の`score`ではなく、vector similarityの下限（0〜1）である。追加検証8問・最大10件では0.4で正解5/8・候補0件2/8、0で正解6/8・候補0件0/8、0.7で全問0件だった。0は取りこぼしを減らす比較候補とするが、負例と引用の取り違えへの影響を測ってから採否を決める（[結果制御の仕様](https://developers.cloudflare.com/ai-search/configuration/retrieval/result-controls/)）。

#### 団体・年度・原典をfilterで限定する

`jurisdiction`を必須とし、年度を混ぜる場合は評価対象年度もfilterで限定する。現索引の`fiscal_year`はnumber宣言だが、数値`2025`で全文検索側が0件になり、文字列`"2025"`では返ることを2問×3反復・2方式で確認した。**現索引での試行は文字列を使う暫定対処とし、複数年度を入れる前に年度の混入と取りこぼしを検証する。** 次の索引では年度をtextで宣言する案と年度別に分ける案を比較する。

原典を限定したい場合は`origin_sha256`、分割後のファイルを限定したい場合は`filename`を使う。`item.key`を返却時に任意の値へ指定する機能としては扱わない。登録したファイル名やメタデータで検索対象を絞る。

filterは等価比較のほか、`$eq`・`$ne`・`$in`・`$nin`・`$lt`・`$lte`・`$gt`・`$gte`を使える。複数のキーはANDで組み合わされる。項目の型と索引の宣言に合わせて使う（[filterの仕様](https://developers.cloudflare.com/ai-search/configuration/retrieval/filtering/)、[メタデータの仕様](https://developers.cloudflare.com/ai-search/configuration/indexing/metadata/)）。

### 検索文と回答用プロンプトの案

検索APIへ渡す検索文と、候補を読むAIへの指示を分ける。検索文は正式名称を優先し、分からない場合は対象・行為が分かる特徴的な語を使う。団体・年度はfilterで限定し、「評価を教えて」のような共通の依頼文を毎回足す必要はない。

| 利用者の問いの例 | 最初の検索文 | 見つからない場合の候補 |
| --- | --- | --- |
| 無電柱化は計画どおり進んでいるか | `無電柱化の促進`（名称が分かる場合） | `電線の地中化`、`電柱をなくす道路整備` |
| 子育ての相談先を知りたい | `子育て 相談 支援` | 候補で確認した事業名・相談窓口名 |

上表は検索文を組み立てる例であり、各文の効果を個別に測った結果ではない。正式名称を知らないときは推測した名称を確定情報として扱わず、候補で確認する。言い換えのまま検索する場合もhybridを使う。

長い文を入れるほど精度が上がるとは言えない。追加検証8問・最大10件では、正式名称だけで正解8/8、名称に年度・目標・実績・評価・方針の依頼を足した文で6/8だった。1回ずつの小標本であり、長さだけの効果は分離していない。最大5件での効果や、最適なプロンプトは未検証である。

候補を読むAIには、次の指示から始める。検索3回まで・全文取得・出典つきの回答は既存の測定手順を引き継ぎ、年度の列と指標の文脈を明示する部分は次の比較で検証する改善案とする。

```text
団体と評価対象年度をfilterで限定し、問いの事業の評価を探す。
1. 正式名称が分かれば名称を優先する。不明なら、対象と行為が分かる
   3文字以上の特徴的な語を含めて検索する。検索は最大3回、各回最大5 chunk。
2. 返された候補は続きも含めて全件取得し、全文を読む。
   0件なら同じ文を一度再試行してよい。未発見なら行政資料の言い方や
   候補で確認した名称で検索し直す。再試行も3回の上限に含める。
3. 同名・関連事業・上位施策を区別する。問いが同名の複数事業を対象にする場合は、
   見つけた全頁を挙げてfound。候補のどの事業を指すか決められなければambiguous。
   3回で見つからなければnot_foundとし、検索範囲と限界を添える。
4. 回答前に対象事業、評価対象年度、指標、計画／実績の行と列を確認する。
   頁に到達しても帰属が確かめられない値は推測せず、不明とする。
5. 目標・実績・評価区分・課題・方向性を、原典sha256・物理頁・連続した引用と
   ともに答える。数値は指標名・単位・年度の文脈も示す。
   指標名だけを目標値にせず、目的の文を数値目標として扱わない。
   資料にない項目はnull。評価資料の金額を財政データの答えには使わない。
```

**「最適なプロンプトを選べば基本的にヒットする」という保証はできない。** 正式名称での候補への到達は今回214/214だったが、AIの最終頁選択は39/40で、正答した174問の引用842項目中145項目（17.2%）を取り違えた。同じ検索文で候補0件になる変動も観測した。検索文、索引の区切り、表の抽出、事業の対応づけ、引用の読み取りを分けて検証する。

## Alternatives Considered

全文検索だけなら正式名称には強いが、今回の言い換えで正解0/80だったため、hybridを選ぶ。通常の最大件数は利用者の指定で5件とする。10〜20件へ増やすと本文量も増えるが、件数の優劣は小標本の追加検証では確定できなかった。

PDFをそのまま入れる方法は登録を簡単にできたが、事業・年度・項目の取り違えが残った。次の比較では、それらの対応を保つ構造化抽出も候補にする。プロンプト変更だけの場合と比べて、引用の誤りと取りこぼしが減るかを測る。

## Cross-Cutting Concerns

試行の公開エンドポイントは無効にする。Gitには設計と試行の内容・結果・考察を残し、実行用コード・固定入力・判定・観測はローカルの`.cache/evaluation-search/`に保持する。cloneだけでの再集計はできない。

### 費用（2026-10-13 の公式文書。課金は 2026-11-01 から）

| 対象 | 毎月の無料枠 | 超えた分 |
|---|---|---|
| 取り込み | 500万 token | $0.75 / 100万 token |
| OCR（画像の処理） | 取り込みと同じ枠 | 追加で $0.50 / 100万 token |
| 保存 | 10 GB-month | $2.00 / GB-month |
| 意味・hybrid の検索 | 1,000回 | $0.75 / 1,000回 |
| 全文検索 | 1,000回 | $0.10 / 1,000回 |

- 評価のシートは1頁あたり約3,000 token（中野区の別冊75頁で 209,255 token、`cl100k_base`）。取り込みの無料枠は月に約1,600頁分で、超えると1,000頁あたり約 $2.3。索引を作り直すと（tokenizer・custom metadata の変更を含む）、取り込みをもう一度数える。
- 保存は PDF の大きさで、中野区の別冊は1頁あたり約90KB。26団体・8,000頁でも約1GB で、無料枠に収まる。原典は別に非公開 R2 に置く。
- 費用で効くのは検索の回数である。AI は一つの問いで何度も検索するので、公開するときは流量の制限と kill switch を置く。

## Validation / Rollout

試行の結果は [`trial.md`](trial.md) に残す。現在は拡大の閾値が未達のため、公開・拡大を進めない。新しい設定・プロンプトを同じ問いで比較し、正解が候補に含まれる割合、頁の選択、負例の該当なし、引用の帰属を別々に測る。判定にも20%の標本不一致があったため、人間の独立判定も必要である。

### 測定条件を先に固定する

1. **索引を作る。** 選定した URL から取得し、sha256 が選定と一致することを確かめた PDF を、大きいものは分けて、メタデータを付けて入れる。
2. **正解の集合を作る。** 両団体の評価の資料の事業名と、marts の目の名前から問いを作り、問いごとに正解の事業の評価（0件も正解）と頁を付ける。候補は機械で出してよいが、正解は人が原典の頁を見て決める。印字から機械的に作る場合（2026-10-13 の測定）は、無作為に抜いた問いの頁との対応を人が確かめた記録を残す（この測定では未実施）。
3. **AI に引かせる。** 呼び出す AI に、団体・年度と問いを渡し、検索の問いを組み立てさせて引かせる。AI が候補を読んで目的の事業の評価を選んだ結果も記録する。
4. **測る。** 次の通常設定は最大5件とし、過去の最大10件の成績とは条件を分ける。分母と合否の閾値は問いと正解を作る前に固定する。設定・プロンプトを選ぶ問いと、最終成績を測る未使用の問いも分ける。
