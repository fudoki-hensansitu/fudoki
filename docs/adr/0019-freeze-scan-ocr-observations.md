# ADR 0019: scan PDFのOCR観測を凍結した補助入力として変換に渡す

状態: 採用（2026-10-11）。実装は未着手で、下の「実装に必要な変更」を別の作業で行う。

## 背景

scan PDFの取り込みでは、OCRの結果をどう変換の入力にするかについて2つの方式が混在している。

- **凍結したOCR結果を入力にする（方式A）**: 132039 武蔵野市の水道会計の変換器は、事前に取得したnative JSON（約10MB）をファイルパスとSHAで受け取る。書式設定の個別訂正22件と見出しの対応36件は、そのnativeのSHAと観測IDに結び付いている。nativeはgitignore配下のローカルファイルにしか無く、補助入力のR2保存は未実装のため、そのファイルを持たないcheckoutやマシンからは再変換できない。
- **変換のたびにOCRを実行する（方式B）**: 削除済みの132241 多摩市の変換器は、変換の中で `scan_ocr` を呼び、ローカルキャッシュを再利用していた。OCRの出力が実行ごとに変われば、観測IDに結び付けた訂正やfingerprintの前提が崩れる。

未着手のscan PDFは約685頁ある（132101 小金井・132055 青梅・132152 国立・132209 東大和・133035 瑞穂など）。どちらの方式にするかで変換器の作り方が変わるため、先に決める。

### 前提

- OCRエンジンはPaddleOCR small（[ADR 0018](0018-paddle-small-for-scan-pdf.md)）だけを対象にする。Apple Visionは比較用に残っているが、取り込みの経路では使わない。
- OCRを実行する環境は、当面は管理者のMac 1台に限る。別のマシン・LinuxでOCRを実行することは求めない。

### 実測

2026-10-11に、同じPDF・同じ頁・同じ既定設定でPaddleOCRを同じMacで繰り返し実行した（詳細と実行条件は [検証記録](../scan-ocr-determinism.md)）。

- native JSONのSHA-256は全7ファイルで異なった。差は所要時間4種とrendererのキャッシュ状態の欄だけだった。
- 文字・座標・confidence・観測ID・観測の順序・描画画素は、132039の10頁（観測4,983件）と132101の4頁（3,354件）で、別プロセス・同一engineの再実行のすべてで一致した。頁の部分集合（132039）とCPU thread数の変更（132101）でも一致した。
- 新しく取得したnativeで132039の書式設定を再生すると、訂正と見出しが参照する観測ID 131件がすべて存在し、訂正22件・見出し36件が元の文字列と枠の照合を通った。R2の保存済み7表と比べた差は、このcheckoutに無い追加crop OCRで読む1セル（とその継承値）だけだった。
- OCRは132039で1頁あたり5.5〜10.0秒、132101の密な見開きで約12〜15秒かかった（M1、他の処理による負荷あり）。nativeは1頁あたり約1〜1.8MB、gzipで約75〜120KBだった。

同じMac・同じ版では、OCRを再実行しても同じ観測が得られる。したがって方式Bでも訂正の結び付けはすぐには崩れない。崩れるのは、OCRの結果を変える要因（paddle系・numpy・pillowの版、モデル、`paddle_ocr.py`、macOS・Xcodeの更新によるCoreGraphics描画、Macの買い替え）が変わったときである。今回はこれらを変えた比較はしていない。

## 決定

OCRは変換器の外で、共通の取得入口から実行する。結果のnativeは**OCR観測の補助入力**として非公開R2に保存し、管理JSONの変換に原典と同じくSHAで宣言する。変換器はOCRを呼ばず、宣言された補助入力だけを読む。方式Aを基本とし、次の点を加える。

1. **補助入力のSHAはOCRの内容だけを表す。** 補助入力には、どの原典のどの頁を読んだか（原典SHA・物理頁・読み取り領域）と、OCRの結果（描画画素のSHA・頁の寸法、観測、nativeの結果）だけを入れる。所要時間・キャッシュ状態・絶対パス・PID・RSSと、実行した環境（package版・モデルとコードのSHA・OS・rendererのbuild）は実行記録として別ファイルに分ける。実行記録は補助入力と同じ場所に保存するが、SHAの対象にも宣言にも含めない。同じMacで取り直せば同じSHAになり、版を上げても結果が同じならSHAは変わらない。SHAが異なれば結果が異なる。所要時間などを含む形式の補助入力は保存・宣言しない。
2. **取得の条件をGitで宣言する。** 原典SHA・物理頁・OCR設定・読み取り領域・再読領域を取得の依頼として宣言し、補助入力はその依頼から作られたものとして管理する。
3. **再取得は検証と更新に限る。** 通常の変換・再構築はR2の補助入力を使う。OCRの結果を変える要因を更新したときは同じ依頼で取り直し、SHAが一致すればそのまま使う。異なれば差分を確認し、訂正の結び付けを見直してから補助入力を差し替える。
4. **保存は最新版だけにする。** 取り込み表と同じく、対象・方向・補助入力のIDで決まる固定keyへ上書きし、全保存の成功後に管理JSONを更新する。1つの依頼を1つのgzipファイルにし、頁ごとには分けない。

個別訂正は、補助入力のSHA・観測ID・セル枠・元の文字列に結び付ける現在の方式を続ける。

## 運用の流れ

| 場面 | この決定での動き | 方式Bでの動き |
| --- | --- | --- |
| 新しい団体の変換器を作る | 取得の依頼を宣言し、`ingestion:ocr` で1回OCRを実行する。以後の書式設定の調整はnativeから変換を繰り返す | 変換のたびにOCRを実行する。キャッシュがあれば再利用する |
| 書式設定・訂正を直して再変換する | 132039の10頁で約1秒。OCRは実行しない | キャッシュがあれば同程度。無ければ181頁の冊で約36〜45分 |
| `.cache/` を消した後や、別のcheckoutで再構築する | R2から原典とnativeを取得して変換する | 全頁のOCRをやり直す。685頁でCPU約1〜3時間 |
| paddle・macOSを更新する、Macを買い替える | 何もしなければ表は変わらない。更新を取り込むときは再取得してSHAを比べ、変わった観測と訂正だけを確認する | 次の変換で黙って新しいOCR結果になる。観測IDや文字が変われば、訂正の照合で変換が止まる。止まらない範囲の差は表へそのまま入る |
| 過去の表の作り方を確かめる | 管理JSONのnative SHAとR2の補助入力で、変換時と同じ入力を再現できる | 当時の版と同じ環境を用意しない限り、同じ入力を再現できない |

## 理由

- **再構築が環境の更新に左右されない。** 管理者のMac 1台に限っても、OS・Xcode・依存の更新と買い替えは避けられない。実測で一致を確認したのは同じ版の範囲だけで、版をまたぐ一致は確認していない。凍結した観測を入力にすれば、更新後も過去の表を同じ入力から作れる。保存設計の「再構築に必要な原典・取り込み表・コード・宣言を保持する」原則と同じ扱いである。
- **OCRの変化を明示的に取り込める。** 方式Bでは、OCRの結果の変化が変換の失敗か、気付かない表の差として現れる。この決定では、再取得と差分確認を変換とは別の作業として行う。
- **変換を速く繰り返せる。** 132039の10頁では、凍結した観測から表を組み立て、保存済みの表と全セルを比べる処理が約1秒だった（Parquetの書き出しは含まない）。キャッシュを失った後の再構築でも、OCRを再実行しない。
- **fingerprintと整合する。** 補助入力のSHAは変換の宣言に含まれるため、fingerprintに入る。fingerprintは実行環境を含めない設計であり、方式Bではpaddle系の版やOSの違いで出力が変わっても変換を古いと判定できない。補助入力を固定すれば、表の入力条件がすべてfingerprintで表される。
- **費用は小さい。** 685頁でも未圧縮で約0.7〜1.2GB、gzipで約50〜85MBの見込みである。

SHAを内容だけに限る理由は、実測で内容が同じでもファイルのSHAが毎回変わったためである。所要時間を含む形式では、取り直すたびに訂正22件のSHAを書き換える必要があり、内容が変わったかどうかをSHAで判定できない。

固定keyにする理由は、取り込み表と同じく最新版だけを保持すれば足りるためである。内容ハッシュのkeyなら上書き途中の失敗でも旧版が残るが、古いkeyの掃除が別に必要になる。対象・方向ごとの逐次実行を前提にする限り、表と同じ手順で十分である。取得したnativeは管理JSONのSHAと照合するため、上書きの途中で失敗しても、古いnativeを黙って使うことはない。

現在の単一アップロードの上限（300MB）は、R2へ送るファイルのバイト数に適用している。補助入力でも、送るgzipファイルの大きさで判定する。上限に近いのは取り込み表のParquetではなく、未圧縮のnative JSONである。132101の一般会計（181頁）では未圧縮で約320MBになるが、gzipでは約22MBになり、1つの依頼を1ファイルにしても上限に収まる。

## 代替案

| 案 | 利点 | 採否 |
| --- | --- | --- |
| 現在の方式Aのまま（ローカルパスで受け取る） | 実装済みで追加作業がない | nativeを持つcheckoutでしか再変換できず、取り直すたびにSHAが変わるため採用しない |
| 方式B（変換のたびにOCRを実行し、ローカルキャッシュを使う） | 補助入力の保存・宣言が不要で、OCRの改善が次の変換に反映される。同じMac・同じ版なら結果は一致した | 版・OSの更新や買い替えで結果が変わったとき、過去の表を同じ入力から作れない。キャッシュを失うと全頁のOCRに数時間かかる。キャッシュを使えば実質は方式Aをローカルだけで行うことになるため採用しない |
| 方式Bに、環境の版をfingerprintへ加える | 環境の変化で表を古いと判定できる | 判定はできても同じ表を作り直せない。更新のたびに全表が古くなり、訂正の照合も同時に崩れるため採用しない |
| OCR観測を取り込み表（Parquet）として保存する | 保存の仕組みを表と共有できる | 観測は財政データの取り込み表ではなく、raw層の表と混ざる。nativeの未変更の出力を保持する方針（ADR 0018）とも合わないため採用しない |
| 補助入力をGitに置く | R2の実装が不要 | 1頁あたり約1〜1.8MBで、685頁では約1GBになる。Gitはコード・宣言を置く場所であり、原典と同じく非公開R2に置く |
| 補助入力を内容ハッシュのkeyで保存する | 上書き途中の失敗でも旧版が残る | 最新版だけを保持する方針では掃除が増えるため採用しない |

## 結果

- scan PDFの変換器は、OCR観測の補助入力・原典・書式設定から表を作る処理になり、変換器の中でOCRを実行しない。新しい団体の変換器は、OCR取得の依頼を宣言し、共通入口で観測を取ってから変換を書く。
- OCRのコード・モデル・依存の更新は、表を自動で古くしない。更新するときは補助入力の再取得と差分確認を明示的に行う。古い観測のまま変換を続けることは許容する。
- 132039の現在の凍結native（SHA-256 `41956f0115d9bac0835fa38959ce1ef96a4ed6a534fd99cf83a5f782d466b2b8`）と追加cropのnativeは所要時間を含むため、そのままでは保存しない。OCRを再実行せず、既存のファイルから実行ごとに変わる欄を取り除いて新しい形式へ変換する。観測は変わらないため、訂正と見出しの対応のSHAを新しいSHAへ機械的に置き換え、同じ表が再生成されることを確認してから保存する。
- 補助入力の保存・宣言・取得入口が実装されるまで、新しいscan PDFの変換器は凍結したnativeをローカルで受け取る現在の形式で作ってよい。宣言は後で補助入力の参照へ置き換える。

## 決めていないこと

- 原解像度の再読（`retry_regions`）とcropの領域指定による読み取りでの再実行一致は測っていない。同じengine・同じ画素を使うため一致を見込むが、実装時に一度確認する。
- paddle系・macOSの更新をまたいで観測が一致するかは測っていない。更新するときに再取得で確認する。
