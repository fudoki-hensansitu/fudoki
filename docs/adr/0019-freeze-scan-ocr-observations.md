# ADR 0019: scan PDFのOCR観測を凍結した補助入力として変換に渡す

状態: 採用（2026-10-11）。実装は未着手で、下の「実装に必要な変更」を別の作業で行う。

## 背景

scan PDFの取り込みでは、OCRの結果をどう変換の入力にするかについて2つの方式が混在している。

- **凍結したOCR結果を入力にする（方式A）**: 132039 武蔵野市の水道会計の変換器は、事前に取得したnative JSON（約10MB）をファイルパスとSHAで受け取る。書式設定の個別訂正22件と見出しの対応36件は、そのnativeのSHAと観測IDに結び付いている。nativeはgitignore配下のローカルファイルにしか無く、補助入力のR2保存は未実装のため、他の環境から再変換できない。
- **変換のたびにOCRを実行する（方式B）**: 削除済みの132241 多摩市の変換器は、変換の中で `scan_ocr` を呼び、ローカルキャッシュを再利用していた。OCRの出力が実行ごとに変われば、観測IDに結び付けた訂正やfingerprintの前提が崩れる。

未着手のscan PDFは約685頁ある（132101 小金井・132055 青梅・132152 国立・132209 東大和・133035 瑞穂など）。どちらの方式にするかで変換器の作り方が変わるため、先に決める。

2026-10-11に、同じPDF・同じ頁・同じ既定設定でPaddleOCRを同じMacで繰り返し実行した（詳細と実行条件は [検証記録](../scan-ocr-determinism.md)）。

- native JSONのSHA-256は全7ファイルで異なった。差は所要時間4種とrendererのキャッシュ状態の欄だけだった。
- 文字・座標・confidence・観測ID・観測の順序・描画画素は、132039の10頁（観測4,983件）と132101の4頁（3,354件）で、別プロセス・同一engineの再実行のすべてで一致した。頁の部分集合（132039）とCPU thread数の変更（132101）でも一致した。
- 新しく取得したnativeで132039の書式設定を再生すると、訂正と見出しが参照する観測ID 131件がすべて存在し、訂正22件・見出し36件が元の文字列と枠の照合を通った。R2の保存済み7表と比べた差は、このcheckoutに無い追加crop OCRで読む1セル（とその継承値）だけだった。
- OCRは132039で1頁あたり5.5〜10.0秒、132101の密な見開きで約12〜15秒かかった（M1、他の処理による負荷あり）。nativeは1頁あたり約1〜1.8MB、gzipで約75〜120KBだった。

同じ環境ではOCRを再実行しても同じ観測が得られた。一方、別のMac・CPU・OS・package版で同じ観測になるかは測っていない。

## 決定

OCRは変換器の外で、共通の取得入口から実行する。結果のnativeは**OCR観測の補助入力**として非公開R2に保存し、管理JSONの変換に原典と同じくSHAで宣言する。変換器はOCRを呼ばず、宣言された補助入力だけを読む。方式Aを基本とし、次の3点を加える。

1. **nativeを再現可能なバイト列にする。** 所要時間・キャッシュ状態・絶対パスは実行記録として別ファイルに分け、補助入力に含めない。同じ環境で取り直せば同じSHAになり、ファイルのSHAがOCRの内容を識別する。
2. **取得の条件をGitで宣言する。** 原典SHA・物理頁・OCR設定・読み取り領域・再読領域を取得の依頼として宣言し、補助入力はその依頼から作られたものとして管理する。
3. **再取得は検証と更新に限る。** 通常の変換・再構築はR2の補助入力を使う。OCRコード・モデル・package・OSを変えたときは同じ依頼で取り直し、SHAが一致すればそのまま使う。異なれば差分を確認し、訂正の結び付けを見直してから補助入力を差し替える。

個別訂正は、補助入力のSHA・観測ID・セル枠・元の文字列に結び付ける現在の方式を続ける。

## 理由

- **再構築に必要なものを保存できる。** 変換の入力が原典・補助入力・コード・宣言で閉じ、OCRを実行できない環境（Linux CIなど）や別のマシンでも同じ表を作れる。これは保存設計の「再構築に必要な原典・取り込み表・コード・宣言を保持する」原則と同じ扱いである。
- **訂正の結び付けが環境に左右されない。** 実測では同じ環境のOCRは観測IDまで一致したが、環境をまたぐ一致は保証されていない。Apple Visionは内部の重みを固定できず（ADR 0017）、OSの更新で結果が変わり得る。凍結した観測を入力にすれば、環境の違いで訂正が外れて再構築が止まることがない。
- **変換を速く繰り返せる。** 書式設定の調整のたびに685頁を読み直すと、CPUだけで約1〜3時間かかる。132039の10頁では、凍結した観測から表を組み立て、保存済みの表と全セルを比べる処理が約1秒だった（Parquetの書き出しは含まない）。
- **fingerprintと整合する。** 補助入力のSHAは変換の宣言に含まれるため、fingerprintに入る。fingerprintは実行環境を含めない設計であり、OCRを変換の中で実行すると、package版やOSの違いで出力が変わっても変換を古いと判定できない。補助入力を固定すれば、表の入力条件がすべてfingerprintで表される。
- **費用は小さい。** 685頁でも未圧縮で約0.7〜1.2GB、gzipで約50〜85MBの見込みである。

決定論的な出力にする理由は、実測で内容が同じでもファイルのSHAが毎回変わったためである。現在の形式のままでは、取り直すたびに訂正22件のSHAを書き換える必要があり、内容が変わったかどうかをSHAで判定できない。

## 代替案

| 案 | 利点 | 採否 |
| --- | --- | --- |
| 現在の方式Aのまま（ローカルパスで受け取る） | 実装済みで追加作業がない | nativeを持つマシンでしか再変換できず、取り直すたびにSHAが変わるため採用しない |
| 方式B（変換のたびにOCRを実行し、ローカルキャッシュを使う） | 補助入力の保存・宣言が不要で、OCRの改善が次の変換に反映される | 同じ環境での一致は実測したが、環境をまたぐ一致・Visionの重みは固定できない。macOSとモデルが無い環境では変換できず、変換のたびに数分〜数時間かかる。キャッシュを使えば実質は方式Aをローカルで行うことになり、保存されないため採用しない |
| 方式Bに、環境の版をfingerprintへ加える | 環境の変化で表を古いと判定できる | 判定はできても再構築はできない。OS・packageの更新で全表が古くなり、訂正の照合も同時に崩れるため採用しない |
| OCR観測を取り込み表（Parquet）として保存する | 保存の仕組みを表と共有できる | 観測は財政データの取り込み表ではなく、raw層の表と混ざる。nativeの未変更の出力を保持する方針（ADR 0018）とも合わないため採用しない |
| 補助入力をGitに置く | R2の実装が不要 | 1頁あたり約1〜1.8MBで、685頁では約1GBになる。Gitはコード・宣言を置く場所であり、原典と同じく非公開R2に置く |

## 結果

- scan PDFの変換器は、OCR観測の補助入力・原典・書式設定から表を作る純粋な処理になる。新しい団体の変換器は、OCR取得の依頼を宣言し、共通入口で観測を取ってから変換を書く。
- OCRのコード・モデル・依存の更新は、表を自動で古くしない。更新するときは補助入力の再取得と差分確認を明示的に行う。古い観測のまま変換を続けることは許容する。
- 132039の現在の凍結native（SHA-256 `41956f0115d9bac0835fa38959ce1ef96a4ed6a534fd99cf83a5f782d466b2b8`）は、所要時間を含む旧形式のままR2へ移せる。訂正の結び付けは変えずに済む。新形式で取り直す場合は、同じ観測であることを比較してから訂正のSHAを機械的に更新する。
- 補助入力の保存・宣言・取得入口が実装されるまで、新しいscan PDFの変換器は凍結したnativeをローカルで受け取る現在の形式で作ってよい。宣言は後で補助入力の参照へ置き換える。

## 決めていないこと

- 別のMac・CPU・Linux・Poppler描画で同じ観測になるかは測っていない。環境をまたいで再取得の一致を求めるかは、必要になった時点で測ってから決める。
- 原解像度の再読、cropの領域指定による読み取り、Apple Vision、複数のOCRプロセスの同時実行での一致は測っていない。
- 1冊が数百頁の場合に、補助入力を頁ごとに分けるか。132101の一般会計（181頁）は未圧縮で約320MBになり、現在の単一アップロードの上限300MBを超える。gzipでは約22MBの見込みで、今回は1つの依頼を1ファイルにする。
- 補助入力のkeyを `id` ごとの固定keyにするか、内容ハッシュのkeyにするか。取り込み表と同じ固定keyと全保存後の管理JSON更新を前提にしたが、実装時に再検討してよい。
