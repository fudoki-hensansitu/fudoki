# ADR 0028: 単位の確かめを全ての PDF 表の保存の関門に置き、印字の合計は表の位置から置く

状態: 採用（2026-10-13）。[ADR 0027](0027-refresh-fingerprints-by-table-content.md) の保存の関門（`storage.prepare_save`）と、検査だけのモジュール（`*_checks.py`）を前提とする。

木の検査は、全段が同じ倍率で間違う（千円の表を円と読む）と検出できない。親も子も同じだけ違い、和は合う。汎用の組み立て（`ingestion/generic/units.py` の `check`）だけが、款の和と印字の歳出合計を比べ、一般会計の合計の桁が単位に合うかを確かめていた。各自治体の変換器・scan の変換器（settlement_statement）の表と、保存済みの表には掛かっていなかった。

款の和＝印字の歳出合計と、一般会計の合計の桁を、変換器を問わず全ての PDF 表の保存の関門で確かめる。規則は `generic/units.py` の `check` と同じものを呼ぶ（二重に実装しない）。モジュールは `ingestion/fiscal/unit_checks.py`（検査だけで、指紋の外）。当てる場所は `run.convert`（汎用・各自治体・scan の直接の経路のどれも通る）、`storage.prepare_save`（`save` と `ingestion:refresh` が共有）、`ingestion:verify` である。止まる表は保存しない。

- 款は、軸の名前（科目・款項・款項目）によらず、親が無く段が「款」のノードとする。
- 印字の歳出合計は保存済みの表に残らない。変換器の対象範囲（`<表ID>.coverage.json`）の語から、歳出合計の行の数字を読む。同じ行の断片をつなぎ、見開きの右頁に続く数字だけの行も読み、その数字を、**同じ頁の款の金額の右端に揃う列**（款の無い頁なら全頁の款の列で一つの見出しに決まるもの）に置く。変換器が申告する金額欄の範囲は読まない（自治体によっては列群全体を1つの箱にしている）。
- 置けない数字は比べない。同じ段階（決算なら支出済額）の合計が異なる値で2つ以上置かれたときも、どれが会計の合計かを決められないので比べない。
- 比べられない表（印字の合計が無い・置けない、scan、保存済みの表）は、今の `units.check` と同じく桁だけを確かめる（一般会計のみ）。分冊（`partial`）は報告だけで止めない。

## 検討した案

| 案 | 利点 | 採否 |
| --- | --- | --- |
| 保存済みの表（ノードの表・金額の表）だけに `units.check` を当てる | 変換器に触れない | 印字の合計が表に残らないので桁しか確かめられず、特別会計は桁の規則も無い。単位の誤りは検出できない |
| 全変換器が印字の合計を返す契約にする | 比べる値が確実 | 各自治体の変換器 17 本を直す。scan は合計の行を捨てている |
| 対象範囲の語から、款の金額の列に合計を置く（採用） | 変換器を変えない。全自治体に同じ規則 | 置けない表は桁だけになる。対象範囲を持たない scan・保存済みの表は桁だけ |
| 変換器が申告した金額欄の範囲で合計を置く | 新しい仕組みが要らない | 131148 は列群全体を1つの範囲で申告しており、別の列の数字を支出済額として置き、正しい表を止めた |

右端の揃えの許容は 2pt とした。6pt にすると、132250 の別表（決算額の列に、別の歳出合計の行がある）の 46,053,000,000 を支出済額として置き、正しい表を止める。

## Consequences

- 比べる強さは、表が対象範囲を持つかで決まる。`convert`・`refresh`・`verify --candidate` は款の和と印字の合計を比べる。保存済みの表だけを当てる `verify` は桁だけで、特別会計は桁の規則が無いので確かめられない。
- scan（settlement_statement）は歳出合計の行を捨てるので、桁だけを確かめる。scan の款の和を印字の合計と比べるには、変換器が合計を返す作業が別に要る。
- 単位の確かめは `unit_checks.py` で直すので、直しても保存済みの表は古く見えず、`ingestion:refresh` は変換をやり直さない（指紋が現在の管理 JSON は対象外）。厳しくしたときは、桁は `ingestion:verify --remote` で、款の和と印字の合計の比較は `ingestion:convert`（ローカルの候補）→ `ingestion:verify --candidate <候補dir>` で全表に当て直す。
- 結果の種類: `matched`（款の和＝印字の合計）、`digits`（一般会計の桁が単位に合う）、`partial`（分冊。報告だけ）、`unchecked`（比べるものが無い）、`stopped`。

## 実測

2026-10-13、`ingestion:refresh --remote` で保存済みの 68 PDF 表（29 管理 JSON のうち 25 が対象）を変換し直して当てた（scan の 1 表を含む）。

| 結果 | 表 | 内訳 |
| --- | --- | --- |
| `matched` | 49 | 款の和が印字の歳出合計と一致 |
| `digits` | 1 | 132012 一般会計。歳出合計の行の数字を款の金額の列に置けず（款の金額の右端に揃う数字が無い）桁だけ |
| `unchecked` | 5 | 132012 の特別会計 2（同上。特別会計は桁の規則も無い）、132071 の下水道事業会計 2（歳出合計の行が無い事業会計の書式）、132055 の後期高齢者医療特別会計（scan。印字の合計を持たず、特別会計に桁の規則も無い） |
| `partial` | 13 | 132292 の分冊（一般会計 13 冊） |
| `stopped` | 0 | |

`ingestion:verify --remote`（保存済みの表。対象範囲が無いので桁だけ）は 68 表すべて一致、20 が桁を確認、13 が分冊、35 は特別会計などで比べるものが無い。scan の 1 表は `refresh` で保存済みの表と同じ中身だった。
