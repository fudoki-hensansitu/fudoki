# ADR 0021: 段の名前と金額の段階への対応は dbt の seed に置き、取り込みには出典の事実だけを求める

状態: 採用（2026-10-11）。同日、金額の段階への対応の置き場を `pipeline/shared/` に改めた（下記）

取り込みのノードの表と金額の表（[ADR 0020](0020-ingestion-outputs-node-tables.md)）を、提供用データの段の名前（款・項・目・事業・節・細目）へ対応づけ、金額欄の出典の見出し（「支出済額」など）を金額の段階（executed など）へ対応づける宣言は、dbt の seed に置く。取り込み側（B）には、その宣言を出典に照らして検査できる事実（ノードの親子と分解の軸、出典に印字された段の見出し・番号・名称、金額欄の出典の見出しと単位、出典の頁）だけを求める。宣言は dbt の intermediate で当て、宣言にない見出しや、宣言が当たらないノード・金額があれば構築を止める。staging の前の入力準備は、保存参照と表の構造だけを検査し、宣言との照合はしない。

## 理由

対応づけは風土記の解釈であり、出典で確認した事実とは性質が違う。たとえば新宿区の決算書の目の欄にある「支出済額」を、提供用データの支出済額として採るのは風土記の判断である。この判断を取り込みに置くと、[保存設計](../prd/ingestion-storage/dd.md)が取り込みから除いた「共通分類への対応」が入り込み、判断を直すたびに取り込みの fingerprint と R2 の表が変わる。

一方で、宣言だけを根拠にすると、宣言どうしが一致しているだけで出典との対応は確かめられない。そのため、照合に使う事実を取り込みの責務として要求する。

宣言を seed にできるのは、PDF の取り込みの出力がノードの表と金額の表に揃い、PDF の staging が書式ごとの SQL を持たなくなるためである。宣言は書式ごとの列名ではなく、見出しの値への対応になり、構築中の結合で引ける。CSV は原文の表のまま取り込み、書式ごとの staging の yml でどの列が款・項・目・節・金額かを宣言する。intermediate でノードの形にした後は、PDF と同じ seed の対応を当てる。

## Considered Options

- **取り込みに段の名前・金額の段階を持たせる**: dbt の宣言は不要になる。判断の修正が取り込みの再実行を伴い、保存設計の境界にも反するため採用しない。
- **staging の yml（列の `meta`）に書式ごとの対応を書く**: 横持ちの表のように列名が書式ごとに違う場合には向く。ノードの表では列が共通で、対応は見出しの値に対して決まるため、表として検査できる seed にする。

## Consequences

- 自治体・表を足すたびに seed に行が増える。行は（自治体・表・軸・深さ）から段の名前への対応と、（自治体・表・軸・深さ・金額の見出し）から金額の段階への対応で、根拠を書く。
- 金額だけの欄に見出しがなく、説明などの欄に印字された金額（見出しが「備考／事業説明」など）は、子の和が親の支出済額と一致することを根拠として seed に書く。
- 設計の全体は [dbt モデルの設計](../prd/fiscal-dbt-models/dd.md) を参照する。

## 改訂（2026-10-11）

金額欄の見出しから金額の段階への対応は、dbt の seed ではなく `pipeline/shared/fiscal_amount_map.csv` に置く。取り込みの保存前の木の検査も、子の金額を親のどの段階と比べるかをこの対応で決めるため、取り込みと dbt の両方が読む。取り込みが dbt の中を読む依存を作らないよう、層をまたいで使うものは `pipeline/` 直下に置く。対応は資料区分と見出しの経路・末尾の語で引き、自治体・表の列は持たない（同じ見出しでも決算書と当初予算書で段階が違うため、資料区分を鍵に含める）。段の名前への対応は dbt の seed（`fiscal_level_map`）のままとする。

## 改訂2（2026-10-11）

段の名前への対応も seed をやめ、共通規則にした（[ADR 0025](0025-level-names-by-shared-rule.md)）。`fiscal_level_map` は削除。金額の段階への対応は共有辞書のまま。
