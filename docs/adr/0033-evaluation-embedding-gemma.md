# ADR 0033: 評価の検索の埋め込みを embeddinggemma-300m（chunk 512）に変え、索引を fudoki-evaluation-v2 に移す

状態: 採用（2026-10-20）。同日に `fudoki-evaluation-v2` を作り、2026-10-21 までに全1,033出典を登録し、2026-10-22 に Worker の binding を切り替えて v1 を削除した（[v2 への移行](../prd/evaluation-search/dd.md#v2-への移行の確かめ)）。[評価の検索の設計](../prd/evaluation-search/dd.md)の頁単位の登録、[ADR 0031](0031-evaluation-text-items-for-unreadable-pdfs.md) の文字の item を前提とする。

本番の評価の検索（`POST /v1/evaluations:search`）は、2026-10-14〜20 の81件のうち20件（24.7%）が8秒の打ち切りで503になった。Worker の中（D1 の kill switch・rate limit・Durable Object の回数）は中央値82ms で、所要のほとんどは AI Search の検索だった（中央値5.3秒）。AI Search を直接引くと、全文検索だけ（keyword）は中央値0.5秒・最大1.3秒で安定し、意味の近さの側（vector）は中央値2.5秒・最大8.3秒だった。インスタンス `fudoki-evaluation-v1` の埋め込み `@cf/qwen/qwen3-embedding-0.6b` を Workers AI で直接呼ぶと、検索文1つで中央値1〜5秒・最大20秒かかった。同じ時間帯に `@cf/google/embeddinggemma-300m` は中央値0.8秒・最大1.7秒、`@cf/baai/bge-m3` は中央値0.7秒・最大1.0秒だった。索引が246 item だった 2026-10-14 にも2〜6秒かかっていたので、遅さは索引の大きさではなく、検索文の埋め込みによる。計測の方法は本文のとおり。生データは調査の作業 dir（`.cache/evaluation-search-latency/`、Git 管理外）に置いたため残っていない。

埋め込みはインスタンスの作成後に変えられない。gemma と bge-m3 は入力が512 token までなので、chunk も 4096 から 512 に下げる必要がある。北区・中野区の2025年度（3出典・246頁）だけを登録した試験用のインスタンス2つで、試行の問い160問（正式名称40・言い換え80・略称40）を、本番の Worker と同じ検索の設定で v1 と同じ時間帯に引いた（試験用のインスタンスは比較の後に削除した）。

| | v1（qwen3・chunk 4096） | gemma・chunk 512 | bge-m3・chunk 512 |
| --- | ---: | ---: | ---: |
| 正式名称 | 40/40 | 39/40 | 37/40 |
| 言い換え | 61/80 | 68/80 | 65/80 |
| 略称 | 39/40 | 38/40 | 38/40 |
| 所要の中央値・p90・最大（秒） | 1.32・3.45・8.22 | 0.74・1.34・4.15 | 0.99・1.61・5.51 |

試験用は246 item、v1 は33,141 item なので、所要の差には索引の大きさも混ざる。全件を登録した v2 で同じ160問を引き直すと、正式名称 39/40・言い換え 60/80・略称 39/40、所要の中央値・p90・最大は0.77・1.55・5.23秒だった（[v2 への移行の確かめ](../prd/evaluation-search/dd.md#v2-への移行の確かめ)）。所要の改善は全件でも残り、言い換えの到達の改善（試験用で 68/80）は全件では再現しなかった。chunk 512 では1頁が中央値1・最大5 chunk（243頁で414 chunk）になり、上位5 chunk に同じ頁が重なるので、返る頁は中央値4になった。

## 決定

- 評価の検索の索引を、埋め込み `@cf/google/embeddinggemma-300m`・chunk 512 token・重なり0の新しいインスタンス `fudoki-evaluation-v2` に移す。ほかの設定（trigram・OCR なし・公開エンドポイント無効・custom metadata・検索の設定）は v1 と同じにする。
- item の単位と key・metadata は変えない（1頁1 item、[ADR 0031](0031-evaluation-text-items-for-unreadable-pdfs.md) の文字の item も同じ）。1頁が複数の chunk になるので、Worker は同じ頁の chunk を順位の高い1つだけ候補にする。最大5 chunk は変えないので、候補は5件以下になる。
- Worker の binding は、v2 で全出典の登録を確かめ、検証1と所要を測ってから切り替える。v1 は切り戻しのために残し、v2 で1週間問題が無ければ削除する。切り替えの後、本番でも v2 が v1 より速かったので、v1 は1週間を待たずに削除した（2026-10-22）。
- 8秒の打ち切りは変えない。

## 検討した案

| 案 | 利点 | 採否 |
| --- | --- | --- |
| A. gemma・chunk 512 の v2 に移す（採用） | 埋め込みが速く安定し、到達は全件で v1 と1問以内 | 全件の登録し直しと測り直しが要る。1頁が複数の chunk になる |
| B. bge-m3・chunk 512 の v2 に移す | gemma と同じく速い | 正式名称が 37/40（92.5%）で、公開の条件（95%以上）を下回った |
| C. 全文検索だけにする | 0.5秒前後で安定し、検索の単価が1/7.5 | 試行では言い換え 0/80・略称 7/40 しか上位10件に入らなかった |
| D. hybrid と全文検索を並べて送り、締切で全文検索に落とす | v1 のままで503がほぼ無くなる | 遅い回は言い換えに弱い結果になり、1要求で検索が2回になる。原因の埋め込みは残る |
| E. 打ち切りを延ばす | 値を1つ変えるだけ | 埋め込みだけで20秒の例があり、中央値の数秒も変わらない |
| F. 自治体・年度でインスタンスを分ける | 1つの索引が小さくなる | 246 item でも遅く、原因の埋め込みは減らない |

## Consequences

- 検索の所要が埋め込みの裾（qwen3 の数秒〜20秒）に左右されなくなる見込み。v2 の全件での所要は [v2 への移行の確かめ](../prd/evaluation-search/dd.md#v2-への移行の確かめ)に記録する。
- 候補が5件より少ない回が増える（同じ頁の chunk をまとめるため）。抜粋は候補の頁の最も順位の高い chunk から作る。
- v1 では本文が取れていた頁が、v2 では `file_content_empty` の `error` になった（頁の PDF で172頁・72出典）。72出典は ADR 0031 と同じく `text_origins` に宣言して文字の item にし、md の先頭に頁の PDF の変換と同じ見出しを付けた（見出しの無い md でも119頁が落ちた）。それでも落ちた調布市の2024年度の1出典だけ、本文を NFKC にそろえる（`nfkc_origins`）。引き金は特定できていない。
- 文字の item は132出典に増えた（ADR 0031 の60出典に72出典を足した）。これらの頁の本文は、AI Search の PDF の変換ではなく pdfium の抜き出しの結果になる。
- 検証1の値は、v2 での測り直しの値に置き換わる。
- 本番の503は減ったが無くならず、杉並区の問いでは AI Search の検索が3〜9秒かかる（[v2 への移行の確かめ](../prd/evaluation-search/dd.md#v2-への移行の確かめ)）。埋め込みを替えても遅い問いが残った。
- v1 を消したので、v1 の設定（qwen3・chunk 4096）には戻れない。戻すには新しいインスタンスに全1,033出典を登録し直す（[切り戻し](../prd/evaluation-search/dd.md#切り戻し)）。
