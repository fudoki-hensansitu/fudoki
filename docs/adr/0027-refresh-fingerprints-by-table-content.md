# ADR 0027: 取り込み表の指紋はコード変化の合図とし、保存し直すかは表の中身で決める。検査だけのコードは指紋から外す

状態: 採用（2026-10-13）。[保存設計](../prd/ingestion-storage/dd.md)の「fingerprintで入力条件の変更を検知する」を補う。fingerprintの計算（原典SHA・scope・変換設定・参照するコードの中身のハッシュ）は変えない。

fingerprintは「表が変わったかもしれない」という合図として持ち続ける。`ingestion:check` は今までどおり、古ければ止める。合図が出たら `ingestion:refresh` が変換をローカルでやり直し、保存済みの表と**中身**を比べる。全表が同じなら管理JSONの `input_fingerprint` だけを書き換える（Gitのみ。R2には書かない）。違う表が1つでもあれば、その管理JSONは書き換えず、増えた・消えた・変わった行の数と例を出す。違いは本当の変更なので、件数と差分を見せ、許可を取って `ingestion:convert --remote` で保存し直す。

共有のコードを直す PR は、`ingestion:refresh` を回して指紋を更新した管理JSONを含める。PR の差分が「どの表の中身が変わったか」を示し、回帰の検査を兼ねる。

あわせて、表の中身を作らず合否だけを決める検査のコード（木の検査 `check_tree`・印字された数字の網羅の検査 `check_digit_coverage` など）を、表を作るコード（`write_tables` など）と別のモジュールに分け、指紋の対象から外す。外すモジュールは `*_checks.py` と名付ける。名前の規則だけでは「検査だけ」を保証できないので、`manifest.dependencies` が `*_checks.py` を見つけたときに、表を書く関数・呼び出し（`write_*`・`write_parquet`・書き込みの `open`・`COPY … (FORMAT PARQUET)` など）がないことを検査し、あれば停止する。検査の関数の移動は、`node_tables.py` を別の作業が直している間は行わず、その merge 後に別の PR で行う（その PR で、`refresh` により全表が「同じ」になることを確かめる）。移動は済んだ: `check_tree` は `ingestion/lib/tree_checks.py`、`check_digit_coverage` と専用の補助は `ingestion/lib/coverage_checks.py` にある。

## 理由

fingerprintはコードのファイルの中身のハッシュなので、1文字変わるだけで、そのコードを import する全表が古くなる。表の中身を変えない変更（`node_tables.py` の `check_tree` の検査だけの変更、コメント、リファクタ）でも、保存済みの表を R2 へ保存し直す手順が要る。汎用のノード生成機（`pipeline/ingestion/generic/`）に寄せるほど全団体が同じコードを共有し、規則を1つ足すたびに全表が古くなる。保存し直しは、変換・R2への書き込み（許可が要る）・管理JSONの更新で、中身が同じなら何も得ない。

「コードが変わった」と「表が変わった」は別の事実である。前者はコードのハッシュで分かり、後者は表の中身を比べないと分からない。前者を後者の代わりにしていたことが、手間の原因である。

## 検討した案

| 案 | 利点 | 採否 |
| --- | --- | --- |
| 変更のたびに `convert --remote` で全表を保存し直す（現状） | 手順が1つ | 中身が同じ表の再保存と許可が毎回要り、共有コードを直すほど増えるため採用しない |
| 検査だけの関数を別ファイルに分け、fingerprintの依存から外す | 検査の変更で古くならない。中身の比較より安い | 単独では採用しない。「検査だけ」を人が分類するので、外したコードが後で表を変えても古いと判定されず、古い表が最新として通る。規則（`*_checks.py` が表を書けない検査）と、検査を厳しくしたときの `ingestion:verify` を前提に、`refresh` と併用する |
| fingerprintを廃し、中身の比較だけで判定する | 指紋の更新がいらない | 中身の比較は原典・R2・変換の実行が要り、CIの `ingestion:check` で回せない。コードの変化を安く知らせる合図は残す |
| **指紋は合図、最後は中身で決める**（採用。上の検査の分離を併用する） | 古い判定は安全側のまま、中身が同じ表は保存し直さない。違う表は差分が見える | 比べ直しの実行時間がかかる。比べる範囲（下記）の外は検出しない |

## Consequences

- 入口は `bun run --cwd pipeline ingestion:refresh [--manifest <path>] --remote [--dry-run]`。`--remote` は原典と保存済みの表を R2 から読むだけで、何も書かない。対象は指紋が古い管理JSONだけで、現在のものは変換しない。
- 比べるのは Parquet のバイトではなく中身（列名・型・行とその順序・値）と、変換が管理JSONに書く表のメタデータ（受領書・注記・件数など）。行の差は、保存済みだけにある行（消えた）、候補だけにある行（増えた）、同じ位置で値が違う行（変わった。並べ替えだけの違いもここに出る）の数と例で示す。
- 保存済みの Parquet とその `sha256`・サイズは変えない。中身が同じなら書き換えるのは `input_fingerprint` だけである。
- 保存前の関門（PDF 表の木の検査・印字された数字の網羅の検査・保存先 key とハッシュ・サイズの検査）を、候補の表に当て直す。中身が同じでも、今の検査で止まるなら書き換えずに止める。関門は `storage.save` と共通の `storage.prepare_save` である。
- 管理JSONの書き換えは、一時ファイルへ書いてから置き換える。比べている間に管理JSONや参照するコードが変わっていれば書き換えない。違う表が1つでもある管理JSONは、一部の表だけを更新することもしない。
- 比べられるのは、同じ原典と同じコードの変換が同じ中身を返す範囲である。text PDF と CSV は決定的で、この前提が成り立つ。scan PDF の OCR は実行ごとに出力が変わりうるので、凍結した観測を補助入力にするまでは、この比較で「同じ」になることを期待しない（[ADR 0019](0019-freeze-scan-ocr-observations.md)）。
- 比べ直しは変換をやり直すので、保存済みの全表を一度ずつ変換する時間がかかる。実測は下の表のとおり。
- 検査のモジュール（`*_checks.py`）を指紋から外すので、検査を厳しくしても保存済みの表は古くならず、厳しくなった検査に落ちる保存済みの表に指紋では気づけない。検査を厳しくした PR は、`bun run --cwd pipeline ingestion:verify --remote` を保存済みの全表に当て、通ることを確かめる。落ちる表は、変換コードか宣言を直して `ingestion:convert --remote` で保存し直す。`ingestion:check` は CI で回るが `ingestion:verify` は R2 が要るので CI では回さない。この手順を人が守ることが、検査を外す代償である。
- 検査のモジュール自身の import は指紋の探索で辿らない。検査のモジュールにだけ届くコードは、合否の判断にしか使われず表を作れないためである。変換器が同じコードを直接 import していれば、その経路で指紋に入る。書き込みの検出は代表的な呼び出しを見るヒューリスティックで、証明ではない。
- 検査のモジュールは表を作らない。変換器が検査の関数の戻り値で表の中身を変えるようにしない（合否・件数・停止の判断にだけ使う）。守られていないと、検査のコードの変更が表を変えても指紋が変わらない。
- 中身が同じことは、財政値が原典と合っていることを意味しない。原典との照合は従来どおり木の検査・網羅の検査・`ingestion:verify` が担う。

## 実測

2026-10-13、作業ブランチで `pipeline/ingestion/lib/node_tables.py` に表を変えないコメント1行を足して確かめた（確認後に戻した）。

| 手順 | 結果 |
| --- | --- |
| `ingestion:check` | `Stale saved table: chuo-general-settlement` で停止 |
| `ingestion:refresh --remote` | 16管理JSONのうち14が `refreshed`（45表すべて同じ）、2（132047の歳出・歳入のCSV。node_tables を import しない）は現在のまま。different・blocked は0。R2への書き込みは0 |
| 管理JSONの差分 | 14ファイル、`input_fingerprint` の45行だけ。Parquetの `sha256`・サイズは不変 |
| `ingestion:check` | 通る（16管理JSON・47表） |
| 所要時間 | 4114秒（68.6分）の逐次実行。原典・保存済みの表のR2取得、全変換、比較を含む。マシン負荷が 100 を超え、他の worker の実行と並行した状況での値で、負荷の低い時間帯の値ではない。管理JSONごとでは 5〜20秒（132039・132063・132071決算・132128・132217）から 889秒（131024）・1006秒（131156）までばらつく |

時間の内訳（変換と比較の割合）は測っていない。保存し直しと違い、R2への書き込みと許可は要らない。
