# ADR 0034: 対象を歳出に限らず、住民がアプリを作るのに要る公開データへ広げる

状態: 提案（2026-10-22）。採用したら AGENTS.md の冒頭と Story を書き換える。

風土記は今、歳出の予算・決算額を事業単位まで集めて配っている（AGENTS.md の冒頭）。名前の由来は、諸国から同じ様式で報告を集めた地誌『風土記』で、対象を支出に限る理由は名前には無い。

ハッカソンでは、coding をしたことがなかった人が、自分の課題を解くアプリを AI で作って発信していた。止まったのは作る段階ではなく、その前後だった。自分の町のデータを探して整形することと、公開先を用意することの2つで止まっていた。後者は既存の vibe coding ツールや Void Platform のような共有のデプロイ環境で解ける。前者を解くものはまだ無い。こうした人が最初に作りたがる題材は、施設・子育て・イベントのような生活のデータだと考えられる（推測。題材の記録はまだ無い）。風土記が今持っているのは歳出だけである。

## 決定

- 風土記の主な役割を「自治体の公開データを集め、API から呼べる形に整理すること」とする。歳出は最初の対象として残し、対象を生活のデータへ広げる。
- 足すデータの条件は、歳出と同じく「公開されているのに、読めない・自治体をまたいで比べられない」ものに限る。すでに読めて比べられるデータを API に載せ直すだけなら足さない。
- 生活のデータは、デジタル庁の自治体標準オープンデータセットの様式で集め、全国地方公共団体コードで歳出と join できる形にそろえる。独自のスキーマは作らない（[ADR 0001](0001-fdp-ocds.md) と同じ考え方）。
- 何を足すかは、利用者が実際に作ろうとした題材から決める。先回りして種類をそろえない。
- 配り方は [ADR 0022](0022-serve-marts-via-worker-d1-rest-and-mcp.md) と同じく、Worker と D1 から REST と MCP に出す。データの種類ごとに操作を足す。

## 検討した案

| 案 | 利点 | 採否 |
| --- | --- | --- |
| A. 対象を生活のデータへ広げ、題材の需要から1つずつ足す（採用） | 作る人が止まる理由を直接取り除ける。歳出と同じ団体コードで join できる | 取り込みの宣言・検査・marts を、データの種類ごとに作る手間が増える |
| B. 歳出だけを続け、生活のデータは利用者が自治体のサイトから直接取る | 範囲が広がらず、歳出の網羅に集中できる | coding 未経験の人は、データを探して整形するところで止まる |
| C. 生活のデータは別の repo・別のサービスにする | 歳出の設計に影響しない | 団体のマスタ・取り込みの宣言・配信の基盤を二重に持つことになる |
| D. 自治体標準オープンデータセットの全項目を先にそろえる | 利用者が来たときに揃っている | 使われない種類の取り込みと保守に手間を払う。歳出の網羅も遅れる |

## Consequences

- AGENTS.md の冒頭（「町の家計簿を作る」）と Story（支出データで判断する人）は、採用したら書き換える。歳出の Core actions は残し、生活のデータの利用者を足す。
- 団体のマスタは歳出と共有する。生活のデータに団体コードが無い場合は、取り込みの段階で付ける。
- 自治体標準オープンデータセットに沿っていない自治体（列名や形式が違う）は、歳出の取り込みと同じく、宣言で列の対応を書いて吸収する。
- 歳出の網羅（東京都の自治体）と、生活のデータの追加は、同じ人手を取り合う。どちらを先にするかは、題材の需要が出た時点で決める。
- [ADR 0002](0002-repo-is-canonical.md) の「配布を API 単独にすることはしない」は、生活のデータにも同じく当てはまる。
