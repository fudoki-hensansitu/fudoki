# ADR 0019: 取り込み表の列の意味づけは dbt の staging 宣言に置き、取り込みには原典の事実だけを求める

状態: 提案（2026-10-11）

取り込み表の列を、階層の段（款・項・目）・金額の段階（予算現額・支出済額など）・原典位置へ対応づける宣言は、dbt の staging モデルの yml（列の `meta`）に置く。取り込み側（B）には、その宣言を原典に照らして検査できる事実（列ごとの単位の原文、金額欄と行の段の見出し、粒度を決める列、原典の物理頁）だけを出力契約として求める。staging の前の入力準備が、宣言と取り込み表の metadata を照合し、食い違えば構築を止める。

## 理由

列の対応は風土記の解釈であり、原典で確認した事実とは性質が違う。たとえば新宿区の `目_計` を予算現額とみなすのは、列の見出しと決算書の様式から風土記が下す判断である。この判断を取り込みの metadata に置くと、[保存設計](../prd/ingestion-storage/design-doc.md)が metadata から除いた「共通分類への対応」が取り込みに入り込み、判断を直すたびに取り込みの fingerprint と R2 の表が変わる。

一方で、宣言だけを根拠にすると、宣言どうしが一致しているだけで原典との対応は確かめられない。そのため、照合に使う事実（見出し・単位・粒度・頁）を取り込みの責務として要求する。

## Considered Options

- **取り込みの metadata に段階・共通の列名を持たせる**: dbt 側の宣言は不要になる。判断の修正が取り込みの再実行を伴い、保存設計の境界にも反するため採用しない。
- **取り込み表の列名を団体共通の名前に揃える**: staging の改名がほぼ不要になる。原典の見出しを保持する取り込みの原則と衝突し、18ある変換器をすべて改修する必要があるため採用しない。列名の揺れは staging の改名で吸収する。
- **seed（CSV）に列の対応表を置き、SQL を動的に生成する**: 宣言を表として検査しやすい。seed の内容をコンパイル時に読むには先に seed をDBへ読み込む必要があり、構築の順序が複雑になるため、表の数が増えて yml の管理が破綻するまでは採用しない。

## Consequences

- 書式ごとに staging の yml と SQL が増える。同じ書式の年度・会計違いは `union all` で一つのモデルにまとめ、宣言を複製しない。
- 取り込みの metadata に事実が欠けている列は、照合できない列として入力準備が一覧にする。一覧に載った列を使う間は、根拠（変換器の検査コードなど）を宣言の説明に書く。
- 設計の全体は [dbt モデルの設計](../prd/fiscal-dbt-models/design-doc.md) を参照する。
