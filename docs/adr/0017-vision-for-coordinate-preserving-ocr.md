# ADR 0017: 座標を保持するOCRの第一選択にApple Visionを使う

状態: scan PDFの既定は[ADR 0032](0032-paddle-onnx-for-new-scan-acquisitions.md)で新しい取得をPaddle（ONNX Runtime）にした（2026-10-20）。それ以前の経緯: scan PDFの既定については[ADR 0018](0018-paddle-small-for-scan-pdf.md)で更新済み（2026-10-09）。Apple Visionは比較用に残し、取り込みの経路では使わない（[ADR 0019](0019-freeze-scan-ocr-observations.md)、2026-10-11）。以下は2026-10-07の比較と決定、および2026-10-09のGoogle Cloud Visionの追加比較の記録。

## 決定

歳出PDFの取り込みでOCRが必要な場合、macOS上ではApple Visionを第一選択にする。今回の比較では、評価した金額・名称・階層位置がPaddleOCRと同じく一致し、継続利用時の処理時間が短かった。文字層を持つPDFは先に文字と座標を抽出し、OCRは文字層を利用できない頁・領域に限定する。

OCRからは未訂正の文字、認識候補のconfidence、頁、座標を取得する。表HTMLの生成を主経路にせず、印刷上の字下げや金額右端を保持して、後段で出典の行・階層を組み立てる。文字単位への分割は必須にしない。Visionのaccurateモードが返す枠を、文字ごとの厳密な座標として扱わない。

PaddleOCR・RapidOCRは再評価用の代替候補として残す。Tesseractと、今回試したGLM-OCR・PaddleOCR-VL・TeleOCRの表生成フローは主OCR候補から外す。既存の取り込み表・実験出力は保持する。未評価のVLの文字検出・座標出力モードまで否定する判断ではない。

## 比較の根拠と範囲

昭島市の[令和7年度一般会計予算書](https://www.city.akishima.lg.jp/_res/projects/default_project/_page_/001/005/264/2-1.ippan.pdf)の物理109頁（印刷105頁）を300dpi、2480×3509pxに画像化した。出典SHA-256は `4662197051b0ec0d9c50e1690c5804d0b31e17dd7d35b972fd272e03068507f8`。きれいなtext PDFの画像化であり、実際のスキャンPDFではない。

| エンジン・設定 | 金額の一致 | 説明名称の一致 | 階層位置の一致 | 推論時間（秒、2回） |
| --- | --- | --- | --- | --- |
| Apple Vision、revision 3、accurate | 48/48 | 36/36 | 36/36 | 0.69 / 0.39 |
| PaddleOCR 3.7.0、PP-OCRv6 medium、CPU | 48/48 | 36/36 | 36/36 | 58.72 / 58.78 |
| RapidOCR 3.9.2、PP-OCRv5 server | 48/48 | 35/36 | 36/36 | 14.97 / 19.07 |
| Tesseract 5.5.1、SPARSE_TEXT | 32/48 | 32/36 | 35/36 | 2.52 / 2.52 |

金額は節欄12個と説明欄36個。名称はNFKC適用後に空白・句読点・括弧等を除いた比較で、全文字の一致を意味しない。階層位置は昭島の既知の書式で金額右端を3群に分けた結果であり、一般的な事業階層の理解や事業と節の紐付けを検証したものではない。

通常OCRの金額は、文字を参照せず枠の重なりで1対1に対応付けて比較した。数値の断片は同じ行・近接した座標による共通ルールで結合し、出典の正解値を使って結合していない。金額のカンマ除去は比較時だけで、未訂正出力は保持した。

時間はモデル取得・初期化を除く少数回の実測。Visionの最初の実行では32.38秒かかり、その後は新しいリクエストでも上表の時間だった。初回が遅かった原因は未特定で、恒常的に0.39秒で処理できるとは保証しない。長時間・大量頁の処理、別ハードウェア、Paddleの別モデルや高速化設定は未評価である。

### 実スキャン1ページでの追加確認（2026-10-07）

多摩市の[令和2年度決算書第4分冊](https://www.city.tama.lg.jp/_res/projects/default_project/_page_/001/004/929/020499.pdf)の物理2頁（印刷75頁）でもVisionを実行した。表は600dpiの1bit画像であり、文字層から取れたのはページ番号だけだった。出典SHA-256は `a6d067d5860a4f2a7ba71386522ec1227fd97b2020fb0c1e6c9bbf4be0c45e4e`。300dpiに描画し、同じ認識設定とrevision 3の明示指定で比較した。

印字された金額109セルを出典画像から目視で転記し、罫線から行・列を対応付けた。全ページでは91/109が一致し、18セルを検出できなかった。金額4列を別々に切り出すと107/109へ改善したが、翌年度繰越額の0を2セル検出できなかった。両試行とも検出した金額に値の不一致はなく、未検出を0で補完していない。名称には `備品購入費 → 備品入費`、`償還金 → 價還金` 等の誤読があった。金額列の切り出しは名称を再評価した試行ではない。

全ページの推論は2.64 / 0.66秒、4列の推論の合計は1.20 / 0.50秒だった。描画・Swiftの起動・コンパイル時間は含まない。最初の全ページ実行はVision内部の `e5rtError` で失敗し、8bit sRGB RGBAへ描き直した後の実行は成功したが、失敗原因は未特定である。この1ページには説明欄の事業階層がなく、座標による階層判定の追加検証にはならない。

この結果から、Visionが高速であることと、検出漏れがないことは分けて扱う。列・領域の切り出しと検出漏れの確認は、本体への反映前に必要な作業として残す。[追加確認レポート](../../.agent/pdf-samples/vision-real-scan/report.html)と[セル照合結果](../../.agent/pdf-samples/vision-real-scan/evaluation.json)はGit管理外のローカル比較資料である。

### Google Cloud Visionとの金額セル比較（2026-10-09）

同じ多摩市の物理2頁（印刷75頁）を、Google Cloud Vision APIの `DOCUMENT_TEXT_DETECTION` でも評価した。CoreGraphicsで300dpi・2480×3509pxに描画した画像をRGBのPNGとして送り、言語ヒントは指定しなかった。描画画像のSHA-256は `a3eb5e68051ad9f8b24d1835213770d26f18e08e88df5a7f5c15e9390be0061f`。全頁を1画像で送る条件と、金額4列を切り出して1リクエストで送る条件を、交互に各3回実行した。

照合には既存の目視転記109セルと、罫線から定めたセル枠を使った。OCRの観測枠の中心をセルへ対応付け、空白と桁区切りのカンマだけを除いて比較した。正解値を使った読み取り領域の選択、未検出の0補完、数字や記号の訂正はしていない。

| エンジン・読み方 | 金額セルの一致 | 未検出 | 観測ありの不一致 | 時間（秒） | 時間の範囲・回数 |
| --- | --- | --- | --- | --- | --- |
| Google Cloud Vision、全頁 | 106/109 | 2 | 1 | 0.85（中央値） | 通信込み、3回 |
| Google Cloud Vision、金額4列 | 108/109 | 0 | 1 | 0.61（中央値） | 4画像を1リクエスト、通信込み、3回 |
| Apple Vision、全頁（既存結果） | 91/109 | 18 | 0 | 0.87 | 推論のみ、1回分 |
| Apple Vision、金額4列（既存結果） | 107/109 | 2 | 0 | 0.52 | 4列の推論の合計、1回分 |
| PaddleOCR、PP-OCRv6 small、全頁・縮小検出（既存結果） | 109/109 | 0 | 0 | 10.60 | CPU推論のみ、1回 |

Googleの一致・未検出・不一致の件数は3回とも同じだった。全頁の未検出は1行目と9行目の翌年度繰越額の `0`。観測ありの不一致は、両条件とも27行目の金額 `1,710,000` を `1,710,000 .` と読んだ1セルだった。出典画像にも金額の末尾付近に小さい点が見える。数字の部分は一致しているが、余分な記号を除いて合格にはしていない。

比較表のApple Visionは、言語補正on・名称語彙18語の既存実行 `minimum-height-0-r0.json` を同じ109セルで再集計した。上の2026-10-07の初期試行とは設定・描画条件を分けて扱う。PaddleOCRは同じSHA-256の画像を使った既存の `det1280` 実行を再集計したもので、検出だけ長辺1280pxへ縮小し、認識は原解像度の画像を使っている。今回これらのエンジンを再実行したものではない。

Googleの時間は画像の送信から応答本文の受信までで、描画・PNG化・認証・照合は含まない。3回の時間は全頁が0.83 / 1.01 / 0.85秒、4列が0.93 / 0.57 / 0.61秒だった。ローカルエンジンの推論時間とは計測範囲が異なるため、表から同じ条件での速度比は算出しない。HTTPリクエストは計6回、処理した画像は計15（全頁3画像、4列12画像）。APIの内部モデルの版は今回の応答から特定していない。

この比較は1頁の金額セルに限る。名称・事業階層・一般的なセル検出・長時間処理・並列処理の性能は未評価であり、現行のPaddleOCR採用方針を変更する判断はしていない。[実行コード](../../pipeline/ingestion/fiscal/observations/google-vision-2026-10-09/benchmark.py)・[照合結果](../../pipeline/ingestion/fiscal/observations/google-vision-2026-10-09/evaluation.json)はGit管理外のローカル比較資料として保存し、同じディレクトリに未訂正のAPI応答も保持している。

## Visionの識別と座標の限界

選定対象はApple Visionの `VNRecognizeTextRequest`。確認した[Appleの公式解説](https://developer.apple.com/videos/play/wwdc2022/10024/)ではrevision 3をLive Textにも使う認識器と説明している。内部モデルの固有名、アーキテクチャの詳細、パラメータ数、重みの版は、今回確認した公開資料では特定できなかった。revisionを内部モデル名や重みのハッシュの代わりには扱わない。

比較時の設定は次のとおり。

- macOS: `Version 27.0 (Build 26A428)`、arm64。
- API: `VNRecognizeTextRequest`、実行時の `request.revision` は3。
- 認識: `.accurate`、`recognitionLanguages = ["ja-JP", "en-US"]`、`usesLanguageCorrection = false`。
- 枠: `VNRecognizedText.boundingBox(for:)` で単語・数値範囲を取得。左下原点の正規化座標を左上原点のpixelへ変換し、72/300でPDFのptに換算。

比較スクリプトはrevisionを明示せず、実行時の値を記録した。本体へ反映するときは対応revisionを確認して3を明示し、実際のOSの版・build、API revision、設定、画像寸法・解像度、抽出コードの版を出典別の宣言・実行結果で識別する。内部重みをGLM-OCRのように取得・SHA-256固定する方法は、この公開APIでは確認できていない。OSや設定を更新した場合は同じ評価入力で再確認する。

今回のVisionは対象金額48個すべてで右端がPDF文字層の枠より外側に出た。差は中央値3.14pt、最大4.43ptで、今回の階層境界をまたぐ誤りはなかった。Paddleの単語枠の差の絶対値は中央値0.72ptだった。ただしPDFの枠は組版の範囲であり、画像上の厳密な正解境界ではない。

Appleの[`boundingBox(for:)`の説明](https://developer.apple.com/documentation/vision/vnrecognizedtext/boundingbox%28for%3A%29)でも、accurateは単語精度の枠を返し、文字に厳密に沿うとは限らないとしている。同説明はUI上の目安への使用を案内し、枠の内容を画像処理へ使うことを避けるよう述べている。風土記で座標を階層判定に使うのは追加の検証を要する選択であり、返された枠による文字の再切り出しを前提にしない。

## 代替案とトレードオフ

- **通常PaddleOCR**: 今回の評価対象はすべて一致し、枠もPDF文字層に近かった。一方、このMacで試したCPU設定は約59秒かかった。Visionの枠の広がりで別書式の階層判定が成立しない場合や、macOS以外で処理する場合には再評価する。
- **RapidOCR**: 金額・階層位置は一致したが、名称に `共済費 → 共济费` があり、約15〜19秒かかった。移植性を必要とする場合の候補として残す。マスタ補正は推定として区別し、未訂正の文字を上書きしない。
- **Tesseract**: AUTOでは金額20/48、SPARSE_TEXTでも32/48で、`3,850 → 850` 等の先頭桁の欠落が残った。今回の金額抽出には採用しない。
- **今回のVLの表生成フロー**: 設定調整後のPaddleOCR-VLとTeleOCR、前回のGLM-OCRでは金額48個が一致したが、個々の金額座標と説明の事業→節→内訳の位置関係を保持できなかった。表の金額出現数が一致しても、位置と親子関係の一致とは扱わない。

Visionを選ぶことでmacOSに依存する。LinuxやCloudflare上で同じOCR処理が動く前提にはしない。Mac上で必要な頁を抽出し、採用した取り込みParquetを固定入力として扱う設計を優先する。Visionの内部重みを独立して固定できない点は、取得可能な重みを固定する方式に比べた再現性の制約として受け入れる。

## 実装状況と残る作業

本ADRは選定の記録であり、当時の `pipeline/ingestion/lib/ocr.py` のllama.cpp＋GLM-OCRはこのとき変更しなかった（その後、旧処理とともに削除した）。取り込みParquetの再生成・採用、dbtの変更もしていない。実装変更はこれまでのTODOとまとめて行う。

本体へ反映する前に、別自治体と実スキャンを含む対象頁で、金額欠落・枠の広がり・階層境界の誤判定を確認する。薄い印字・傾き・小さい数字・見開きも対象にし、款・項・目の継承から取り込みParquetまでの対応を検査する。印字された合計や別欄の数字がない場合に、検算を精度保証の代わりにしない。長時間処理の速度とメモリも未評価である。
